# Переделка страницы /parts под каталог поставщика — дизайн

## Контекст и цель

Второй, отдельный этап проекта интеграции с поставщиком OPTFM — см. [спеку синхронизации](2026-08-03-optfm-supplier-integration-design.md), где эта переделка была сознательно вынесена за рамки. После первой синхронизации на сайте появляется ~9000 товаров с деревом категорий (`OptfmCategory`, минимум 3 уровня вложенности). Текущая страница `/parts` — полностью клиентский компонент, который грузит **все** товары через `/api/allproducts` и фильтрует на клиенте по плоским строкам `category`/`subcategory`. Это не масштабируется на такой объём и не будет удобным ни для покупателей, ни для бизнеса.

Цель — единая публичная страница `/parts`, современная, быстрая и читаемая на любом размере экрана, удобная и для клиентов, и для дела (порядок, конверсия) — без отдельного «внутреннего» вида для персонала.

## Архитектура

**Маршруты:**
- `/parts` — корень каталога: список категорий верхнего уровня + поиск
- `/parts/[...categoryPath]` — catch-all для категории/подкатегории любой глубины (тот же паттерн, что уже используется у `/services/[...slug]`, переделанного на серверный рендеринг в этой же сессии)

Оба — серверные компоненты Next.js. Товары запрашиваются напрямую из MongoDB с пагинацией на сервере (`skip`/`limit`) — это и есть главный фикс масштабируемости: раньше грузилось всё, теперь — только одна страница списка за раз.

**Товары из вложенных подкатегорий.** Если пользователь заходит в широкую категорию (например «Запчасти для iPhone» без уточнения модели), нужно показать товары из всех дочерних категорий, а не только напрямую привязанные к этой. Решается через `$graphLookup` по дереву `OptfmCategory` при каждом заходе на страницу категории — дерево маленькое (259 узлов), запрос дешёвый, отдельного материализованного пути не нужно (YAGNI).

**`OptfmCategory` требует поля `slug`.** Сейчас в модели есть только `name` — для красивых URL нужно добавить `slug` (уникальный) и сгенерировать его для всех уже синхронизированных категорий (используется существующий `generateUniqueSlug`).

**Поиск** — отдельная, лёгкая реализация внутри `/parts` (текстовый индекс MongoDB по `Product.name`), не переиспользует общий `/api/search`: тот смешивает услуги/новости/акции в одной выдаче и не пагинирован — для каталога с 9000 товаров это не подходит. Никакой прежней логики не трогаем.

**Сортировка и фильтр цены** — параметры запроса (`?sort=price_asc|price_desc&minPrice=&maxPrice=&page=&q=`), применяются на сервере в MongoDB-запросе, не в браузере.

## Компоненты и адаптивность

**Страница категории:**
- Хлебные крошки (переиспользуется существующий `useBreadcrumbs`/`BreadcrumbContext`)
- Плитки подкатегорий, если есть
- Панель сортировки + фильтр цены + поиск — на мобильном сворачивается в компактную панель с кнопкой «Фильтры», не занимает экран целиком
- Сетка карточек товара: 1 колонка на телефоне, 2–3 на планшете, 4+ на десктопе; на карточке — фото, название, цена, кнопка «В корзину» без обязательного перехода на страницу товара
- Пагинация внизу — номера страниц; на мобильном — компактный вид («← 3 из 214 →»)

**Дерево категорий** — боковая панель на десктопе, отдельный экран/выпадающее меню на мобильном; разворачивается по клику, не показывает сразу все 259 узлов целиком.

## Что вне рамок этого проекта

- Отдельный/расширенный вид для персонала — не нужен, один и тот же интерфейс для всех (решено в брейнсторминге).
- Изменение общего `/api/search` — не трогаем, поиск в каталоге отдельный.
- Фасетные фильтры сверх цены (бренд, наличие и т.п.) — не запрошены, добавлять не будем (YAGNI).
