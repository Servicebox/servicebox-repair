# Интеграция с API поставщика OPTFM (Fashion Mobile) — дизайн

## Контекст и цель

У сайта появился доступ к API поставщика запчастей и аксессуаров OPTFM (Fashion Mobile, `https://optfm.ru/api/`). Нужно регулярно (раз в сутки) забирать оттуда каталог товаров вместе с деревом категорий, применять собственную наценку и превращать их в полноценные `Product` — такие же, как товары, введённые вручную через админку: показываются на `/parts`, продаются через корзину/оформление заказа, попадают в фиды Яндекс.Маркета и Google.

**Реальные параметры, подтверждены живым запросом к API 2026-08-03:**
- Всего категорий: 259, дерево минимум до 3 уровней вложенности (`parent_id` / `depth_level`)
- Всего товаров в наличии: 9013 (метод `catalog.getElementList` отдаёт только то, что есть в наличии — без числа остатка, просто присутствие/отсутствие в выдаче)
- У каждого товара несколько цен в массиве `prices` — используем цену с `id: 4` (name: "Оптовая") как закупочную базу для наценки; она же в тестовых запросах оказывается первой в массиве, но код должен искать по `id`/названию, а не полагаться на порядок
- Доступ к API привязан к IP прод-сервера (`185.221.215.248`) — с локальной машины разработки запрос блокируется WAF поставщика («protobyte_antiparsing», 503 «too many requests»); тестирование и сама синхронизация должны выполняться только на проде

**Границы этого проекта:** только конвейер синхронизации (категории → товары → цены → фото → БД), запускаемый ежедневным cron. Переделка страницы `/parts` под дерево категорий и пагинацию — отдельный, самостоятельный проект, будет специфицирован и реализован позже. До той поры `/parts` продолжает работать как сейчас (загружает все товары и фильтрует на клиенте) — с ростом каталога станет заметно медленнее, это осознанный временный компромисс.

## Архитектура

### Новая модель `Category`

Дерево `parent/children`, по образцу уже существующей модели `Service` в этом проекте:

```js
{
  name: String,
  parentId: ObjectId (ref Category, null для корня),
  depthLevel: Number,
  supplierSectionId: String (unique, id раздела у поставщика — ключ для upsert),
  sort: Number,
  description: String,
}
```

### Расширение модели `Product`

Существующие поля не меняются и не удаляются — товары, введённые вручную через админку, продолжают работать как есть. Добавляются новые:

```js
{
  categoryId: ObjectId (ref Category, необязательное — только у товаров поставщика),
  supplierSource: String (например 'optfm', необязательное),
  supplierProductId: String (id товара у поставщика, unique среди документов с этим полем — партиальный индекс),
  supplierPriceRaw: Number (закупочная цена "Оптовая" до наценки — нужна, чтобы пересчитать new_price при изменении % наценки без повторного похода к API),
}
```

Для обратной совместимости с существующими потребителями плоских `category`/`subcategory` (текущий `/parts`, YML-фиды Яндекс.Маркета и Google) — при синхронизации в эти строковые поля автоматически кладётся имя ближайшей категории/подкатегории из дерева. Ничего в существующем коде фидов/страницы менять не нужно.

### Конфиг наценки

Новая коллекция с одним документом (по образцу уже существующей `BonusConfig` для ставки кэшбэка):

```js
{
  markupPercent: Number,
}
```

Пересчёт `new_price = supplierPriceRaw * (1 + markupPercent / 100)` выполняется на каждой синхронизации (так что смена процента в админке применится к уже загруженным товарам на следующий ночной прогон, либо сразу — через ручной запуск).

## Механизм синхронизации

### Низкоуровневый клиент API

`src/lib/optfm/client.js` — обёртка над `fetch` для POST-запросов к `https://optfm.ru/api/` с `auth_id`/`auth_key` из переменных окружения. Между запросами — обязательная пауза (несколько сотен миллисекунд), при ответе 503 — повторная попытка с увеличивающейся задержкой (WAF поставщика реально блокирует за частые запросы, подтверждено вживую).

### Синхронизация категорий

`src/lib/optfm/syncCategories.js` — постранично забирает `catalog.getSectionList` (лимит 500, всего 259 записей — укладывается в один запрос, но код всё равно должен уметь листать страницы), сохраняет/обновляет `Category` по `supplierSectionId` (`upsert`), вторым проходом простраивает `parentId`, сопоставляя `parent_id` поставщика с уже сохранёнными `supplierSectionId`.

### Синхронизация товаров

`src/lib/optfm/syncProducts.js` — постранично забирает `catalog.getElementList` (лимит 1000, ~9013 записей, около 10 страниц), для каждого товара:
1. Находит цену «Оптовая» в массиве `prices` (по `id === 4` либо по названию, содержащему «опт», регистронезависимо — не полагаемся слепо на позицию в массиве)
2. Применяет текущую наценку из конфига
3. Ищет `Category` по `section_id` товара → `supplierSectionId`
4. Делает `upsert` в `Product` по `supplierProductId`; для новых товаров генерирует уникальный `slug` (переиспользуется существующий `generateUniqueSlug`)
5. Если локального файла изображения для этого товара ещё нет — скачивает через `catalog.getImage`, обрабатывает тем же способом, что и остальные загрузки на сайте (`sharp` → `webp`, сохранение в `/public/uploads/optfm/`). Для уже импортированных товаров изображение повторно не скачивается — это принципиально: при 9013 товарах ежедневное перескачивание всех фото было бы избыточным и медленным. Первая синхронизация (все фото новые) займёт заметное время с учётом пауз между запросами; последующие — только для товаров, которые появились с прошлого раза.

После прохода по всем страницам — товары поставщика (`supplierSource: 'optfm'`), не встретившиеся в этом прогоне, помечаются `isActive: false` (мягкое «удаление», тот же принцип, что уже используется в проекте для товаров) — трактуется как «пропал из наличия у поставщика».

### Расписание

Отдельный скрипт `scripts/sync-optfm.mjs` (по образцу уже существующих одноразовых скриптов проекта вроде `migrate-service-slugs.mjs`), вызывающий `syncCategories()` затем `syncProducts()` последовательно. Регистрируется системным `cron` на проде (например, `0 3 * * *`, чтобы не пересекаться с рабочими часами) — вызов `node scripts/sync-optfm.mjs >> /var/log/optfm-sync.log 2>&1`. Доступ к API поставщика привязан к IP сервера — скрипт не будет работать при запуске с локальной машины разработки, тестируется только на проде (через SSH, как уже делалось при подготовке этого дизайна).

## Админка

Минимально необходимое:
- Поле процента наценки в существующем разделе настроек (по паттерну уже существующей настройки ставки кэшбэка) — `GET`/`POST` роут, аналогичный `crm/bonuses/rate`
- Кнопка «Синхронизировать сейчас» — вызывает тот же код, что и ночной cron, синхронно или в фоне, для случаев, когда нужно обновить каталог раньше расписания

Отдельный интерфейс управления категориями/товарами поставщика не строится — это часть будущей переделки `/parts`.

## Обработка ошибок

- Каждый вызов API — с ретраями (несколько попыток с задержкой) при 503/сетевых сбоях
- Обе синхронизации (категории, товары) идемпотентны — безопасно перезапускать вручную, при сбое посередине, или просто в рамках ежедневного cron; ничего не задваивается благодаря `upsert` по `supplierSectionId`/`supplierProductId`
- Если API поставщика недоступен на момент cron — скрипт логирует ошибку и завершается без изменений; уже загруженные данные в БД не откатываются и не удаляются
- Простая защита от параллельного запуска (кнопка «Синхронизировать сейчас» нажата, пока идёт ночной cron): конфиг наценки хранит `syncInProgress`/`lastSyncStartedAt` — если синхронизация уже идёт, повторный запуск отклоняется с понятным сообщением, а не стартует параллельно

## Что осознанно не входит в этот проект

- Переделка `/parts` под дерево категорий и пагинацию (отдельный будущий проект)
- Учёт точного количества товара на складе (API поставщика этого не отдаёт — товар либо есть в выдаче, либо нет)
- Наценка по категориям/индивидуальная (сейчас — единый процент на все товары поставщика)
- Полноценный интерфейс управления категориями/товарами поставщика в админке
